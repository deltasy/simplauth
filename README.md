## Overview

This project is a monorepo (using npm workspaces) focused on keeping the frontend and backend strictly synchronized. The entire route definitions and data schemas reside in a shared package, ensuring end-to-end type safety.

The application is divided into 3 main modules: **authentication, user management, and admin features (RBAC)**.

The frontend is deliberately lightweight, as most validation and authentication logic is handled by the backend. The authentication and authorization system was built with security by design, preventing malicious interference and data leaks. Sessions rely on JWTs (JSON Web Tokens):
- **Access Token:** Exposed to the frontend but stored in memory (to prevent XSS attacks). It has a short lifespan and can only be generated by the backend via the refresh token.
- **Refresh Token:** The primary and most secure token, stored in an HttpOnly and SameSite=Strict Cookie (mitigating XSS and CSRF attacks). It has a long lifespan and is strictly backend-facing. It is "burned" (invalidated) every time a user revalidates the Access Token, neutralizing replay attacks by malicious actors.

## Features

The code implements the following core flows:

- **Authentication:** Login, registration, logout, and silent session renewal using refresh tokens.
- **Users:** Profile page (`/me`), data editing, and soft account deletion.
- **Admin:** Dashboard to manage permissions (member vs. admin) and restore soft-deleted users.
- **Frontend:** Landing page, authenticated user home, login and registration flows, and fallback (not found) pages built with React and Tailwind CSS.

## API Routes and Documentation

The backend does not rely on hardcoded strings for route definitions. Instead, routes are dynamically built from objects in the shared package (e.g., `routesMetadataV1`). This ensures the frontend and backend always point to the correct URLs, eliminating typo-driven bugs.

**Interactive Documentation:**
Upon starting the backend, automatically generated documentation via Scalar (inferred directly from the Zod schemas) is available at:
- **[http://localhost:3000/api/v1/docs](http://localhost:3000/api/v1/docs)**

There you can inspect contracts, expected payloads, and test API calls straight from the browser.

## Architectural Decisions

Key engineering choices that drove the development:

### 1. Role-Based Access Control (RBAC)
The application enforces RBAC. The user database model includes a permissions table (e.g., `MEMBER` and `ADMIN`). The API protects routes by scalably verifying the user's permission level, isolating administrative capabilities (such as account restoration) exclusively to authorized roles, preventing unauthorized interventions.

### 2. Authentication and Sessions
The flow leverages Access and Refresh Tokens. This enables silent session renewals without forcing frequent user logins, while providing the authority to remotely revoke access if a security breach occurs.

### 3. Single Source of Truth (SSoT)
To avoid desync, route contracts and schemas are centralized in the shared workspace (`shared/src/routes/v1.metadata.ts`). All request validation is handled via Zod. Any route mutation on the API instantly reflects across the frontend, backend, and documentation.

### 4. Automated Documentation
By leveraging the shared Zod schemas, API documentation is auto-generated using Scalar (`scalar.config.ts`). The documentation behaves as a direct mirror of the underlying code, nullifying the risk of deprecated or out-of-sync specs.

### 5. Platform Engineering
The **shared** workspace is treated as an internal library named **`@simplauth/shared`**, which is built during the development process to prevent TypeScript typing errors. The project is an authentic monorepo: `node_modules` are centralized at the root, and each workspace (**shared, simplauth-api, simplauth-web**) maintains a lean `package.json` with strict dependencies and clean path aliases to avoid *relative import hell*.

### 6. Continuous Integration (CI)
A GitHub Actions pipeline (`build.yaml`) is configured to run on every push or PR. It executes unit tests (Vitest) and integration tests (Supertest) to block regressions before they reach the main branch. Every API route is thoroughly tested.

### 7. API Versioning
From day one, the API was designed with explicit versioning (e.g., `/api/v1`). If structural breaking changes occur in the future, a `v2` can be deployed without breaking legacy clients. Each version maintains its own metadata (e.g., `/api/v1/v1.metadata.ts`).

```text
└── package.json           # Workspace definitions and global scripts
```

# ▶️ How to run the project

Thanks to Docker Compose, you don't need to run `npm install` locally to spin up the application.

At the project root, run:

```bash
npm run build
```

This script provisions the `.env` files by copying the sample templates and spins up all containers (database, backend, and frontend).

> **Note:** Once the Docker images are built and environments are set, you only need to run `npm run dev` for subsequent startups.

**URLs:**
- Web (Frontend): [http://localhost:5173](http://localhost:5173)
- API (Backend): [http://localhost:3000](http://localhost:3000)
- API (Docs): [http://localhost:3000/api/v1/docs](http://localhost:3000/api/v1/docs)

## Root Scripts

These are the main shortcuts configured in the root `package.json`:

- `npm run build`: provisions envs and spins up Docker services from scratch.
- `npm run dev`: spins up Docker Compose services (use after the initial build).
- `npm run dev:web`: spins up only the frontend server on the local terminal.
- `npm run test:unit`: runs backend unit test suites.
- `npm run test:integration:local`: runs API integration tests against the current local database.
- `npm run actions`: quick shortcut to stage all, commit --amend, and force push.
